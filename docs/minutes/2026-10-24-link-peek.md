# リンクの一時プレビュー拡張

- ユーザーはX等でリンク先をページ上のモーダルとして開き、領域外クリックで閉じる機能を希望。拡大ボタンを押したときだけ通常の新規タブにする。Arcの参考画像を添付。
- 参考機能はArcのPeek。OSの別ウィンドウを出す要望ではない。
- 開くトリガー（全サイトの外部リンクの通常クリック／Shiftクリックのみ／Xの外部リンクだけ通常クリック）について確認中。
- 既存の検索ランチャーとは別の拡張として同じリポジトリ内で管理する構成が適している。
- 実装調査ではiframeによるリンク先表示がサイト側の埋め込み制限（X-Frame-Options、CSP frame-ancestors等）の影響を受けることを確認。Arc本体と同等の全サイト対応を約束しない。参考画像のYahooニュースも実際の表示可否の確認が必要。
- 全サイトの外部リンクを通常クリックで開く仕様をユーザーが選択。feat/link-peekブランチにLink Peek 0.1.0として追加。
- 元のページにHTML dialogを重ね、独立した拡張機能フレーム内でリンク先をiframe表示する。閉じる・拡大以外の常時説明文は置かない。元のページとタブ数を維持し、拡大操作時だけ現在表示中のURLを新規タブで開く。
- Yahooニュースの公開レスポンスがX-Frame-Options: DENYであることを確認。対応として、表示元タブID＋拡張機能が開始元のサブフレームに限定したセッションルールでX-Frame-Optionsだけ除外。CSPやCookieには触れない。閉じる・元ページ移動・タブ終了時にルールとプレビュー情報を削除。
- サイトのCSP frame-ancestorsで拒否された場合はプレビュー不可表示にし、明示操作でタブを開く。自動で別タブやOSウィンドウを作らない。
- iframe内リンクの遷移を拡張フレーム経由で行い、リダイレクトと現在URLを追跡。Escは記事内にフォーカスがある場合にも対応。内部リンク・修飾キー・中央クリック・ダウンロードは原則元の動作を維持。有効／無効は拡張機能アイコンで切り替え可能。
- frontend-testing-debuggingスキルの手順を使用。Browser plugin not availableのため既存Playwright/Chromiumを使用。製品の閉じたShadow DOMは変更せずCDPでボタン位置を取得して実際のクリックを行った。
- ローカルの2オリジンのHTTPテストサイトで、通常クリック時にタブが増えないこと、領域外クリック、記事内Esc、プレビュー内遷移後の拡大URL、リダイレクト、X-Frame-Optionsの限定例外と閉じた後の削除、CSPを維持した拒否表示、元ページの厳しいframe-src、内部リンク維持を確認。実行時ページエラーなし、閉じた後のsession情報と例外ルールは空。
- 1280x800と390x844の表示を確認。Yahooニュースの実ページもデスクトップ幅でプレビューできることを確認。スクリーンショットは/tmpに保存。実際のログイン済みX・Diaでは未検証。
- Node自動テストは新拡張7件＋既存拡張20件、配布ZIP統合テスト4件を通過。Python標準ライブラリのパッケージ生成で本体ZIPとWindows用ZIPを生成。
- Windows PowerShellでprepare.ps1を実行し、C:/Users/zakki/AppData/Local/LinkPeek/extensionに配置した。ブラウザへの新規読み込みと既存ページの再読み込みはユーザー操作が必要。
- 検索ランチャーや既存公開リリースは変更していない。新しい拡張のストア公開は行っていない。

- ユーザーからWindows側配置先が見つからないと報告。prepare.ps1を再実行し、Windows PowerShellのGet-ChildItemでC:/Users/zakki/AppData/Local/LinkPeek/extensionにmanifest.jsonほか7ファイルの存在を確認。WSLの/mnt/c側からは同じパスが見えないため、以降はWindows側で確認した絶対パスを直接案内する。

- ユーザーのエクスプローラーでも同じWindows絶対パスが存在しない画像を確認。こちらのPowerShell結果とユーザー側の表示が一致せず、配置済みと断言した案内を訂正。原因は未確定のため同じコピー操作を繰り返さず、公開作業ブランチのGitHub ZIPを直接ダウンロードする手順へ変更した。GitHub APIから実際にZIPを取得し、extensions/link-peek/src/manifest.jsonを含むこととZIP整合性を検証した。

- ユーザーからWSLから通常コピーできるはずとの指摘。PowerShell経由ではなく、WSLのmkdirとcpで/mnt/c/Users/zakki/AppData/Local/LinkPeek/extensionへ直接配置し、WSL側で7ファイルを確認した。前段でこの直接コピーを先に試さずダウンロードへ迂回した案内は修正した。

- ユーザーのDiaでXの投稿内ニュースリンクを試行。元ページを再読み込み後、クリックの横取りとモーダル表示は動作したが「このページはプレビューできません」と表示された。対象の投稿または記事URLを確認中。実際のリンク先が未特定のため、CSPやサイト仕様による制限とはまだ断定しない。

## Xのt.coリンク読み込み修正（0.1.1）

- ユーザー提供の公開投稿https://x.com/xRINGx/status/2113902445764247596から、公式の埋め込み用エンドポイントでニュースリンクhttps://t.co/Znh3Mer5tXを特定した。
- 現行版のChromiumで同じリンクを試し、t.coがHTMLとJavaScriptの中間ページを返す→そこからYahooへページ主導で移動する→拡張機能開始元に限ったX-Frame-Options例外が効かずnet::ERR_BLOCKED_BY_RESPONSEになることを再現した。
- HEADではChrome向けの転送先が分からなかったため、t.coだけCookieなしGETを使用し、HTTP転送の最終URL、meta refresh、JSON形式のlocation.replaceの固定文字列を解析する修正を実施。ダウンロードしたスクリプトは実行しない。通常URLは事前取得せず、ヘッダー例外の範囲も広げない。
- fix/link-peek-x-navigationで0.1.1に更新。registerの応答で解決したURLをviewerへ渡し、記事を拡張フレームから直接読み込む。プレビュー内の短縮リンク遷移にも同じ処理を適用。意図的なnet::ERR_ABORTEDは拒否表示にしない。
- 新規プロファイルのChromiumで、指定されたt.coリンクから該当Yahoo記事の実ページまで表示され、failure=falseになることを確認。修正前には同じリンクでfailure=trueを確認済み。
- Nodeテスト32件＋配布ZIP統合テスト4件通過。変更履歴・プライバシー説明を更新。Diaでの再確認には拡張機能と元のXページの再読み込みが必要。

- 最終確認として、短縮URLから記事のh1見出しが表示されること、拡大ボタンで解決後の記事URLが新規タブに開くこと、一時ルールが解除されることを確認。WSLからWindows側のLinkPeek/extensionへ0.1.1を直接コピーし、manifestのバージョンを確認した。
